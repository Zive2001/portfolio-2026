P / 01 case study

Azure Cost Rescue

Cloud cost engineering · anonymized client engagement

role Cloud engineering: diagnosis, refactor, handover
timeline [confirm: e.g. ~3 weeks, part-time]
stack Azure · Azure DevOps · Docker · SQL
outcome ~59% monthly spend reduction · ~$20K/year · zero capacity loss
−59% monthly cloud spend
/ the one-liner

An enterprise Azure tenant had drifted to ~$2,900/month with no clear owner for most of the bill. I mapped every dollar to a purpose, right-sized what was over-provisioned, and put governance in place so it wouldn't creep back. Spend landed at ~$1,200/month — a ~59% cut — with no loss of capacity or reliability.

/ the situation

The tenant had grown the way most do: organically, under delivery pressure, with each new service provisioned for "whatever's safe" and nobody circling back once the deadline passed. By the time it reached me, the monthly bill had roughly [confirm: doubled over ~X months] and no single person could account for more than a fraction of it. That's the real problem with cloud cost — it's rarely one catastrophic mistake, it's a hundred defensible small decisions that never got revisited. The bill wasn't broken. The feedback loop was.

/ diagnosis: what was actually wrong

I started in Cost Management and refused to touch anything until every meaningful line item had an owner and a reason. Three patterns accounted for most of the waste:

  • Compute sized for a peak that never came. The database tier [confirm: which — e.g. an elastic pool / vCore-based SQL] was provisioned for a worst-case load that showed up a few hours a week, if that. The tenant was paying 24/7 for headroom used single-digit percentages of the time.
  • A network topology optimized for convenience, not cost. Resources were laid out to be easy to wire together, which quietly generated avoidable egress and a couple of redundant components that duplicated work already done elsewhere.
  • A CI/CD pipeline that leaked. Build agents and ephemeral environments were spun up per run and [confirm: not consistently torn down], so short-lived infrastructure was being billed as if it were permanent.

None of these are exotic. That's the point — the value wasn't in finding something clever, it was in being the person who actually went line by line and asked "does this still need to exist, at this size?"

/ approach

My rule going in: no reliability sacrificed for the number. It's easy to slash a cloud bill by under-provisioning and creating an outage six weeks later — that's not a win, it's a deferred incident. So every change had to survive the real peak, not the average. I sized to observed usage plus a defensible margin, and I changed one class of thing at a time so I could attribute any regression to a specific move rather than guessing.

/ the work
  • Right-sized the data tier to real usage with scaling configured for the genuine peaks, so the headroom is there when it's actually needed and not paid for when it isn't.
  • Refactored the network topology to cut avoidable egress and remove the redundant components, keeping the paths that mattered and deleting the ones that only existed out of habit.
  • Tightened the pipeline so ephemeral resources die when the job does — build infrastructure that exists for the length of a run and no longer.
  • Instrumented the outcome so cost is now visible per owner, not a single opaque number at month-end.
/ outcome

Monthly spend dropped from ~$2,900 to ~$1,200 — roughly a 59% reduction, on the order of $20K/year — with no loss of capacity and no reliability regression [confirm: add any real before/after signal, e.g. "query p95 latency unchanged"]. More importantly, the tenant came out of it legible: someone can now look at the bill and know what each part is for.

/ keeping it down

The refactor is the easy half. The half that lasts is governance, so the same drift doesn't happen again in six months: cost mapped to owners, a budget with alerts, and the expectation that provisioning gets revisited rather than set-and-forgotten. A cost rescue that isn't paired with a feedback loop just resets the clock — this one closed the loop.
